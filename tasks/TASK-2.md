# Этап 2. MVP

## Цель

Реализовать спроектированный на этапе 1 контракт: сервис на FastAPI с данными в PostgreSQL, миграциями alembic и разделением на слои, который поднимается одной командой через docker compose.

## Что нужно сделать

1. Обновите `develop` после merge этапа 1 и поднимите этап в `pyproject.toml`:

   ```bash
   git switch main && git pull && git switch develop && git merge main
   ```

   ```toml
   [tool.course]
   stage = "2_mvp"
   ```

   С этого момента CI поднимает ваш сервис и гоняет контрактные тесты `contract_tests/stage_2/`.
2. Реализуйте сервис в `app/` со слоями:
   - `app/api/` — роутеры FastAPI и схемы запросов и ответов, без бизнес-логики;
   - `app/service/` — правила: нормализация текста, загрузка словаря, поиск подсказок;
   - `app/repository/` — запросы к PostgreSQL через SQLAlchemy 2.x.
3. Настройте миграции alembic (`alembic init alembic`) и опишите таблицу первой миграцией. Приложение не создаёт таблицы само (`Base.metadata.create_all` не используется): миграции применяются при старте контейнера, например `alembic upgrade head && uvicorn ...`.
4. Напишите `Dockerfile` сервиса и `docker-compose.yml` в корне репозитория:
   - сервис `app` публикует порт 8000, uvicorn слушает `0.0.0.0:8000`;
   - сервис `db` — PostgreSQL с `healthcheck`, порт наружу не публикуется;
   - `app` стартует после готовности `db`: `depends_on` с `condition: service_healthy`.
5. Все настройки — из переменных окружения. Реальные значения в `.env` (он в `.gitignore`), в репозитории — `.env.example` со всеми переменными, которые читает приложение. CI создаёт `.env` копированием `.env.example`, поэтому значения в нём должны подходить для запуска.
6. `GET /health` отвечает 200 `{"status": "ok"}`, только когда PostgreSQL доступен (выполните `SELECT 1`), иначе 503. По нему CI понимает, что сервис готов.
7. Напишите не меньше 5 своих тестов в `tests/`. Тесты проверяют логику — например, нормализацию текста и порядок выдачи, — а не то, что вызвался мок.
8. Добавьте в README раздел «Запуск»: как поднять сервис и прогнать тесты.
9. Если по ходу реализации контракт в `docs/openapi.yaml` изменился — обновите спецификацию.

## Контракт

| Метод | Путь | Тело | Ответ | Коды |
|---|---|---|---|---|
| PUT | `/phrases` | `{"phrases": [{"text": "python tutorial", "weight": 10}, ...]}` | `{"loaded": 2}` | 200; 422 — пустой список, пустой `text`, `weight < 0` |
| POST | `/phrases` | `{"text": "...", "weight": 1}` | `{"id", "text", "weight"}` | 201; 409 — фраза уже есть; 422 |
| GET | `/suggest?q=<префикс>&limit=<K>` | — | `{"query": "py", "suggestions": [{"text", "weight"}, ...]}` | 200; 422 — пустой `q`, `limit` вне 1–50 |
| GET | `/health` | — | `{"status": "ok"}` | 200; 503 — БД недоступна |

- **Нормализация**: нижний регистр, обрезка пробелов по краям, повторяющиеся пробелы схлопываются в один. `"Python  Tutorial "` и `"python tutorial"` — одна и та же фраза. Нормализуются и фразы словаря, и префикс в `q`.
- **`PUT /phrases`** — загрузка словаря: фразы, которых нет, добавляются, у существующих обновляется `weight` (upsert по нормализованному тексту). Фразы, которых нет в запросе, остаются. `weight` по умолчанию 1, не меньше 0. `loaded` — число уникальных после нормализации фраз в запросе. Если одна фраза встречается в запросе дважды, побеждает последнее значение. Изменения видны в `/suggest` сразу, без перезапуска.
- **`POST /phrases`** — одна фраза. `text` в ответе — нормализованный, `id` — целое число. Если такая фраза уже есть (с учётом нормализации) — 409.
- **`GET /suggest`**:
  - только фразы, которые начинаются с нормализованного префикса;
  - сортировка по `weight` по убыванию, при равном весе — по `text` по возрастанию;
  - `limit` по умолчанию 10, допустимо от 1 до 50;
  - `query` в ответе — нормализованный префикс;
  - нет совпадений — 200 и пустой список, а не 404;
  - в объекте подсказки ровно два поля: `text` и `weight`;
  - символы `%` и `_` в префиксе — обычные символы. Если ищете через SQL `LIKE`, экранируйте их.
- Пустым считается и текст из одних пробелов: `text` или `q`, у которых после нормализации ничего не осталось, — 422.
- `text` длиннее 200 символов — 422.
- Ошибки — JSON `{"detail": "..."}`, ошибки валидации — стандартные 422 FastAPI.
- Тела ответов тесты сравнивают целиком: лишних полей в них быть не должно.
- Словарь переживает перезапуск сервиса.

Что проверяет CI (`contract_tests/stage_2/`):

- все пункты контракта выше по HTTP, чёрным ящиком: загрузка, upsert, вес по умолчанию, 409, регистр и пробелы, порядок при равных весах, лимит, пустая выдача, `%` и `_` в префиксе;
- словарь из 5 000 фраз загружается быстрее 20 секунд, поиск по нему — быстрее секунды;
- после `docker compose restart app` словарь на месте;
- операции (метод + путь) в `docs/openapi.yaml` совпадают с живым `GET /openapi.json`. `/health`, `/metrics`, `/docs`, `/openapi.json` в сравнении не участвуют.

## Критерии приёмки

- CI зелёный.
- Слои api / service / repository разделены, в роутерах нет бизнес-логики.
- Таблицы создаются миграциями alembic.
- `.env.example` совпадает с тем, что читает приложение; `.env` и секретов в репозитории нет.
- Не меньше 5 своих тестов, и они проверяют логику.
- В README есть раздел «Запуск».

## Как проверить локально

```bash
make check           # линтеры, типы и ваши тесты
make up              # создаёт .env из .env.example (если его нет) и поднимает compose
make test-contract   # контрактные тесты этапа 2 против поднятого сервиса
make down            # остановить и удалить данные
```

Тест с перезапуском контейнера можно временно пропустить: `uv run python contract_tests/course.py test-contract -m "not restarts_containers"`. В CI он запускается всегда.

Посмотреть, что сервис пишет в лог: `docker compose logs app`. Документация API, которую генерирует FastAPI: http://localhost:8000/docs.

### Если CI красный

Откройте упавший прогон на вкладке Checks в PR:

- `lint` или `unit-tests` — то же, что `make check` локально;
- `meta` — неверное значение `stage` в `pyproject.toml`, сообщение скажет, какие допустимы;
- `stage-1-architecture` — сломали что-то в `docs/`;
- `contract` — разверните шаг, который упал:
  - «wait for /health» — сервис не поднялся. Причина — в шаге «docker compose logs» ниже: там вывод вашего приложения и БД;
  - «contract tests» — в выводе имя упавшего теста и сообщение, что ожидалось и что пришло. Тесты лежат в `contract_tests/stage_2/`, их можно прочитать.

## Типичные ошибки

- **uvicorn слушает `127.0.0.1`.** Внутри контейнера это адрес только самого контейнера, снаружи сервис недоступен. Нужно `--host 0.0.0.0`.
- **`/health` отвечает 200, пока БД ещё не готова.** Тогда тесты стартуют раньше времени и падают на первом же запросе. `/health` должен реально сходить в PostgreSQL.
- **Порт не 8000.** Тесты ходят на `http://localhost:8000`, в compose нужно `"8000:8000"`.
- **Таблицы создаются из кода** (`create_all`), а миграций нет или они не применяются при старте.
- **`.env` в репозитории.** Удалите из git (`git rm --cached .env`), проверьте, что он в `.gitignore`. Значения, которые туда попали, считайте скомпрометированными.
- **Фразы хранятся ненормализованными**, а сравниваются нормализованными — появляются дубли и не работает 409. Нормализуйте при записи.
- **Поиск по префиксу через `LIKE` без экранирования** — запрос `50%` находит всё, что начинается на «50».
- **Загрузка 5 000 фраз по одной** (5 000 отдельных `INSERT` с коммитом каждого) не укладывается во время. Вставляйте пачкой, например `INSERT … ON CONFLICT DO UPDATE` на много строк сразу.
- **Порядок при равных весах случайный** — в `ORDER BY` нужен второй ключ, `text`.
- **`openapi.yaml` не обновлён** после изменения маршрутов — CI перечислит, какие операции есть только в спецификации, а какие только в коде.
- **ruff ругается на порядок импортов в миграциях.** `make format` исправит сам.
- **Добавили зависимость — закоммитьте `uv.lock`.** Ставьте пакеты через `uv add <пакет>`: он обновит и `pyproject.toml`, и `uv.lock`. CI ставит зависимости строго по локу и с несинхронным локом падает.
- **Файл compose называется не `docker-compose.yml`.** CI ищет именно это имя в корне репозитория.
