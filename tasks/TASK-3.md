# Этап 3. Масштабирование

## Цель

Убрать PostgreSQL с горячего пути — самого частого запроса сервиса: подсказки по популярным префиксам отдаются из Redis, а выбор подсказки обновляет популярность асинхронно, через очередь. Измерить эффект нагрузочным тестом.

## Что нужно сделать

1. **Сначала снимите базовые числа — до любых изменений.** На коде этапа 2 заполните `loadtest/locustfile.py` (сценарий — в разделе «Нагрузочный тест» ниже), поднимите сервис и запустите:

   ```bash
   make up
   make loadtest
   ```

   Сохраните итоговую таблицу locust: это колонка «до» в отчёте. На этапе 2 эндпоинта `POST /queries` ещё нет — в замере «до» оставьте только `/suggest`.
2. Обновите `develop` после merge этапа 2 и поднимите этап:

   ```toml
   [tool.course]
   stage = "3_scaling"
   ```

3. Допишите переменные подключения к Redis в `.env` и в `.env.example` (CI создаёт `.env` копированием `.env.example`). Добавьте в `docker-compose.yml` сервис `redis` с `healthcheck`, порт наружу не публикуется. `app` стартует после готовности `redis`.
4. **Кэш или индекс подсказок в Redis.** Выбор за вами:
   - кэш готовых ответов на пару «префикс, limit»;
   - индекс в Redis — например, sorted set на префикс.

   Главное — изменения словаря (`PUT`/`POST /phrases`) и популярности должны быть видны в выдаче, то есть кэш надо инвалидировать. Подсказки по уже запрошенному префиксу должны отдаваться при остановленном PostgreSQL.
5. **Учёт выбора через очередь.** `POST /queries` не пишет в PostgreSQL, а кладёт событие в очередь в Redis — Streams, list или библиотека, на ваш выбор. Отдельный обработчик (воркер) читает очередь и увеличивает счётчик выборов фразы. Варианты:
   - сервис `worker` в compose из того же образа, с другой командой — например, `python -m app.worker`;
   - фоновая задача внутри `app`. Тогда в `ARCHITECTURE.md` объясните, почему так.
6. Добавьте столбец для счётчика выборов **новой миграцией** — первую не редактируйте, она уже применена.
7. Реализуйте `POST /queries` и добавьте его в `docs/openapi.yaml`.
8. `/health` проверяет и PostgreSQL, и Redis.
9. Не меньше 3 новых своих тестов.
10. Повторите нагрузочный тест с теми же параметрами и заполните раздел README «Нагрузочный тест».
11. Допишите в `docs/ARCHITECTURE.md` раздел `## Что изменилось на этапе 3`: что уехало в Redis, как инвалидируется кэш, как устроен воркер, что происходит с событиями, если воркер упал.

## Контракт

| Метод | Путь | Тело | Ответ | Коды |
|---|---|---|---|---|
| POST | `/queries` | `{"text": "python tutorial"}` | пустое тело | 202; 422 — пустой текст |

- `POST /queries` фиксирует, что пользователь выбрал подсказку. Текст нормализуется так же, как фразы. Неизвестная фраза — тоже 202, выбор просто игнорируется.
- Итоговый вес фразы = исходный `weight` + число выборов. В `/suggest` поле `weight` показывает итоговый вес, сортировка — по нему.
- Изменение видно в `/suggest` не позднее чем через 5 секунд.
- Если PostgreSQL остановлен, `GET /suggest` по уже запрошенному префиксу возвращает тот же список. Запись в словарь в это время может отвечать 503, это не проверяется.
- Весь контракт этапа 2 продолжает действовать.

Что проверяет CI (`contract_tests/stage_3/`, плюс все тесты `stage_2/`):

- `POST /queries` — 202 с пустым телом, для неизвестной фразы тоже 202, пустой текст — 422;
- фраза A с весом 5, фраза B с весом 1; 10 выборов B → не позднее чем через 5 секунд выдача `[B (11), A (5)]`;
- префикс запросили → `docker compose stop db` → тот же префикс отдаёт тот же список → `docker compose start db`. Тест сам возвращает БД в исходное состояние.

Словарь для теста загрузите один раз в начале — в обработчике события `test_start`. В `on_start` этого делать не стоит: он выполняется у каждого из 50 пользователей, и словарь загрузится 50 раз. Чтобы locust не заводил отдельную строку статистики на каждый префикс, передайте `name="/suggest"`.

## Критерии приёмки

- CI зелёный.
- Подсказки действительно берутся из Redis: при попадании в кэш запроса в PostgreSQL нет.
- Кэш инвалидируется при изменении словаря и популярности, и в `ARCHITECTURE.md` объяснено как.
- Воркер подтверждает обработку события после записи в БД — или в README честно сказано, что при падении воркера события теряются.
- Раздел README «Нагрузочный тест» с параметрами, таблицей и выводами.
- Счётчик выборов добавлен новой миграцией.
- Не меньше 3 новых своих тестов.
- В `ARCHITECTURE.md` есть раздел «Что изменилось на этапе 3».

## Типичные ошибки

- **Кэш не инвалидируется** — после `PUT /phrases` или выборов `/suggest` отдаёт старый список, и тест с 10 выборами не дожидается нового порядка. Простой способ: номер версии словаря в Redis входит в ключ кэша и увеличивается при каждом изменении.
- **Кэш есть, но горячий путь всё равно ходит в БД** — тест с остановленной БД это поймает.
- **Тело ответа 202 не пустое.** `return None` из обычного эндпоинта FastAPI даёт тело `null`. Нужен `Response(status_code=202)` или `response_class=Response`.
- **Вес в выдаче не учитывает выборы** — `weight` в ответе должен быть итоговым.
- **Воркер забирает событие и не подтверждает обработку.** С Redis Streams без `XACK` события копятся в списке ожидающих; со списком и `LPOP` событие теряется, если воркер упал между чтением и записью в БД.
- **Воркер не запущен.** `docker compose ps` — есть ли `worker` и не перезапускается ли он в цикле; `docker compose logs worker`.
- **`/health` не проверяет Redis.** Тогда CI начинает тесты, пока Redis ещё не готов.
- **Тест с остановленной БД падает на ожидании `/health`.** При остановленном PostgreSQL `/health` отвечает 503 — так и должно быть, тест ходит не в `/health`, а в `/suggest`.
- **Старая миграция отредактирована вместо новой.** На уже поднятой базе alembic её не применит: он считает её уже применённой.
- **После `docker compose start db` первые запросы падают** — в пуле остались мёртвые соединения. Помогает `pool_pre_ping=True` у `create_engine`.
- **Разные параметры нагрузки «до» и «после»** — сравнение теряет смысл.
